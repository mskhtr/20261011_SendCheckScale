# そこそこ詳しい人が言う「できる」「できない」の正体

老害にだけはなりたくないと思っていた。経験の範囲を仕様だと言い、知らない見た目をその場で閉じる人。手持ちの手順の外を、土地の外として返す人。それだけにはなるまいと思っていた。

なっていた。パレットに絵がない要望を、「ユーザーフォームではできません」と返していたときのことである。その言葉は、自分の手順の端を、土地の端として渡していた。老害の顔は、頭ごなしの拒否だと思っていた。実際についていたのは、見積もりと信用の顔だった。だから、自分では老害だと分からなかった。

そこそこできる人が言う、出来る出来ないはAIによって崩壊した。

送信前チェックの画面（`frmSendCheck`）は、ユーザーフォームのデザイナに部品を一つも置いていない。空のフォームにコードを貼り、起動した瞬間に枠とラベルを積んで、宛先のカード、細いスクロールバー、押すと色の変わるボタン、添付のツリーを作る。マウスホイールは、フォームが表示されているあいだだけ Windows のフックで受け取っている。

この画面を見て「自分の知っているユーザーフォームではできなかった」と感じたのは、見間違いではない。ツールボックスに並んでいる完成品の範囲では、あの見た目は出てこない。知識がなかったので改善要望に「できません」と答えていた、という記憶もそのままでよい。その答えは、その時点の判断として筋が通っていた。

崩れたのは、その「できません」が測っていたものの正体である。

## どんな感覚か

地図の端を、海岸だと思っていた。あとから分かったのは、海岸ではなく、自分の地図の端だった、という感覚である。

熟練した人の「できる／できない」は、冷たい仕様調査ではない。依頼を聞いた瞬間に、体のほうで返ってくる見積もりである。頭に部品が浮かばない。過去に近い画面で苦戦した記憶がある。ツールボックスを開いても、それらしいコントロールがない。そこで口から出る「できません」は、怠けでも謙遜でもなく、今の自分の手順では引き受けられない、という職業上の結論である。

AI に同じ要望を渡すと、その結論が短時間で画面になる。否定されたように感じるのは腕の優劣ではない。見積もりに使っていた体温計が、別のものを測っていたと分かったときの、足場の抜けである。

これまで一つの言葉に畳んでいたものが、少なくとも三つに裂ける。

1. 自分の手持ちの手順で、今日から再現できるか。
2. その実行環境の部品を組み合わせれば、画素として成立するか。
3. できたとして、自分や次の人が直せる大きさか。依頼に対して抱える価値があるか。

人間が口にしていた「できません」は、ほとんどいつも 1 だった。そして 1 は、2 や 3 と区別されないまま、相手にはプラットフォームの限界として届いていた。「ユーザーフォームでは無理です」は、聞いていた側には「VBA では無理です」になる。

AI が実演したのは 2 である。1 が否定されたように見えるのは、2 の実演が、1 の不在を隠してしまうからである。3 は、画面が動いたあとも残っている。ここが、感覚の芯である。基準が嘘だったのではない。一つの目盛りに、別々の問いが重なっていた。

## なぜ「できません」が正しい答えに見えたか

ユーザーフォームの教育は、完成したコントロールから始まる。ラベル、テキストボックス、リストボックス、コマンドボタン、フレーム。デザイナに置き、プロパティを変え、その部品のイベントプロシージャを書く。この作法に慣れるほど、「できる見た目」はパレットに絵があるものに寄っていく。

パレットに絵がない要望は、次のように変換される。

- カードで人を見せたい → リストボックスにはその見た目がない → できない
- ホイールで流したい → フレームはホイールを受け取らない → できない
- 細いバーをドラッグしたい → 標準のスクロールバーの見た目は指定できない → できない
- 平らなボタンで、押したときだけ色を変えたい → コマンドボタンでは足りない → できない
- 実行時に作った部品をクリックしたい → デザイナに置いていないので、フォームに Click が生えない → できない

どれも、パレットの完成品としては本当である。Frame は標準ではホイールに反応しない、と `modWheelScroll` の先頭にも書いてある。知識がそこで止まっていれば、「できません」は調査結果として正しい。

止まることには理由がある。知らない手順を「maybe」で受けると、終わる保証がない。API の宣言、64 ビット、フックの解除、部品を何個もイベントに結びつけるクラス。途中で崩れたとき、依頼者に返す言葉が残らない。だから熟練者は、見えた範囲の外を「できない」に丸めて、日程と信用を守る。その丸めは、現場では美徳ですらある。

丸めた瞬間に、1 が 2 の顔をする。自分の手順の外が、土地の外に見える。

## この画面がやったこと

新しいユーザーフォームが生えたわけではない。パレットの完成品を使うのをやめ、もっと小さい部品に戻した。

| 画面で見えているもの | 実際の部品 |
| --- | --- |
| 宛先のカード、部署の折り返し、クリックで開く | 実行時に積んだ `Frame` と `Label`。開閉は座標の再計算 |
| 列のホイールスクロール | 表示中だけのマウスフック。カーソル下のフレームの `ScrollTop` を動かす |
| 右の細い溝とつまみ | `Label` を溝とつまみにし、クラスモジュールでドラッグする |
| フラットなボタン、押下で色が変わる | `Frame` の上に `Label`。`MouseDown` / `MouseUp` をクラスで受ける |
| 実行時に作ったカードのクリック | `WithEvents` のクラスを部品の数だけ持ち、フォームの手続きを呼ぶ |
| 倍率と、作業領域に収まるか | モニタの作業領域と DPI を見て、全体の倍率を決める |
| 添付の階層、確認の印 | 同じく枠とラベル。印もコントロールを塗って置いている |

クリックのクラス（`ClsCardClick`）、ボタンのクラス（`ClsButtonHandler`）、つまみのクラス（`ClsScrollDrag`）、ホイールのモジュール（`modWheelScroll`）。フォーム本体は、それらを起動時に組み立てる手順である。デザイナの上に「カード」というコントロールは、最後まで存在しない。

知っていれば一段ずつ納得できる。`Controls.Add` で枠を足せる。クラスに `WithEvents` を書けば、実行時の部品のクリックを受けられる。ユーザーフォームが受け取らないメッセージは、Windows のフックで拾える。個別には、VBA の掲示板に昔からある話である。

難しかったのは、その個別を一つの画面の文法にすることである。空のフォーム、全部実行時生成、見た目の単位はカード、イベントはクラス、スクロールは自作、倍率は起動時に一度決める。この文法を先に持っていない人には、要望の一つ一つが「パレットにない」に見える。文法を持っている側には、同じ要望が「枠を何枚足すか」に見える。

## なぜこちら側では簡単に見えたか

簡単だったのは、探索の費用の払い方が違ったからである。

人間が未知の手順に入るとき、費用は時間だけでは終わらない。途中で投げ出す自分、依頼者への説明、動いたあとの保守、64 ビットで落ちる恐怖。それらが先に立つので、最初の一歩が「調査」ではなく「受諾」になる。受諾できないなら、能力の問題としてではなく、判断として断る。

こちらは、その受諾を会話の中で先にやってしまう。パレットの完成品で足りないと判断した瞬間に、枠とラベルとクラスと API へ降りる。降りる先の部品は、学習データのなかでは接続済みである。ホイールが届かない、実行時の部品にイベントがない、ボタンの色が変わらない。これらは別々の欠落ではなく、同じ欠落（完成品のコントロールには、見た目と入力が閉じている）への同じ種類の回避である。一度その回避を画面の前提にすると、次の改善要望は新しい研究ではなく、同じ前提への追記になる。

見ている側には、要望のたびに「またできた」と映る。作っている側の手順は、要望の数が増えても種類が増えていない。カードの開閉も、列のフィルタも、添付の展開も、確認の印も、座標と色と、クラス経由のクリックである。簡単に見えた正体は、才能の密度というより、前提を変えたあとの枝葉の安さである。

ただし、枝葉が安いことと、ソフトウェアが軽いことは別である。フォームのコードは数千行ある。名前の接頭辞でクリック先を振り分け、フックは閉じるときに外し、倍率は起動のたびに測る。会話の中では一要望が一応答に見えても、残る成果物は「ラベルを上手に置いただけ」ではない。

## 崩れたあとに残るもの

足場が抜けたあとも、基準が不要になったわけではない。目盛りが一つでは足りなくなった、というだけのことが多い。

次に誰かから見た目の要望が来たとき、以前の「ユーザーフォームでは無理です」は、そのままでは使わないほうがよい。代わりに、裂れた三つの問いを順に置く。

**画素として成立するか。** 枠、ラベル、実行時生成、クラスでイベントを受ける、足りない入力は Windows に聞く。この範囲なら、パレットに絵がないことは、もう断る理由にならない。カード、自作のバー、平らなボタン、ホイールは、今回それで通った。

**直せる大きさか。** 画素ができても、読み手が前提を共有していなければ、次の修正はまた「できない」に戻る。この画面を直す人は、デザイナのプロパティではなく、`CreatePersonCard` や `ApplyCardLayout` の座標を読む。その読み方を渡さないまま画面だけ渡すと、できた事実だけが残り、1 の地図は相手の中で更新されない。

**抱える価値があるか。** MSForms は、ウェブページではない。アニメーション、仮想化した長い一覧、読み上げ、部品ごとの自由な描画は、今回のやり方を延長しても素直には出てこない。そこを同じ文法で押し切ると、行数だけが増える。そのときは「環境が拒否している」のではなく、「この文法で抱えるには大きい」と答える。これは 1 への退行ではなく、3 の判断である。

以前の「できません」のうち、守るべきだった部分は 3 に残っている。日程、信用、引き継ぎ。捨ててよい部分は、パレットに絵がないことを土地の端だと思う部分である。

## この感覚を、次の依頼でどう使うか

崩れた基準の代わりに、体に戻せるルールは短い。

要望を聞いたとき、最初に探すのはパレットの完成品ではない。その見た目が、矩形と文字とクリックに分解できるかである。分解できるなら、知らないことは「できない」ではなく、「この画面の文法にまだ追記していない」である。分解した先が矩形で済まないなら、そこで初めて、環境の限界として断る。

そして、できた画面を見たあとに残る気持ちは、二つのまま持っておいてよい。一つは、過去に断った要望の一部は、土地の外ではなかったという改訂。もう一つは、会話の中で簡単だったものは、成果物の中では簡単ではないという保留。前者だけだと、次から何でも受けてしまう。後者だけだと、またパレットの端を海岸だと思い直してしまう。

今回の画面は、その両方を同じフォルダに置いている。空のユーザーフォームから始まること。そして、その空を埋めたコードが、もう手でざっと追える長さではないこと。
